# otel-html M2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship milestone M2 of otel-html: a Logs explorer (Logs / Patterns / Traces grouping, facets, severity histogram, views), a log detail panel, and log↔trace cross-linking (Logs tabs in the trace and span panels, a Trace tab in the log panel).

**Architecture:** The writer already stores every log verbatim in columnar chunks (M1). M2 adds a real log rollup (severity buckets, log facets, Drain patterns) and makes the trace index point at log chunks, so a trace→logs jump loads one shard. The viewer gets a log data layer that mirrors the span one (`LogQueryRun` shared by an eager and a windowed strategy, each chosen per signal), and the Logs UI is built from the same shared components as Traces, generalized where they were span-only (facet panel, histogram card, query bar, results table, chart views). The selection store learns a selected log and per-page modes and views, and a single carry-over rule decides what survives a jump between explorers.

**Tech Stack:** unchanged from M1 (TypeScript 7, React 19, ECharts 6, Zustand 5, wouter 3, TanStack Table/Virtual, Base UI, Zod 4, Lezer OTTL, Vitest 5, Playwright 1.64). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-25-otel-html-design.md` (§7.3, §7.6, §8.3, §8.5, §8.4 Logs tabs, §16). Mockup: `docs/superpowers/specs/2026-10-25-otel-html-mockups/03-log-explorer.html`. M1 plan for conventions: `docs/superpowers/plans/2026-10-25-otel-html-m1.md`.

**Scope boundaries (M2 only):** The log panel's **Metrics** tab, span Metrics tab and the embedded metric grids are M3. "Copy as dashboard widget", saved views and the Views ▾ menu contents stay as in M1. No live tail. Log records are never deduplicated (§16).

**Plan-level calls (flag at review if wrong):**
- **Patterns.** The writer runs Drain over every log and stores the clusters in `data/rollups/logs.js`; that is the unfiltered Patterns landing (exact). With a filter or free text, the viewer runs the **same** `Drain` class over the matched logs: exact under budget, labeled partial above (§16). Chunks do not get a pattern-id column, so the chunk format is unchanged and `merge` across versions keeps working.
- **Eager vs windowed is chosen per signal.** Each signal's decoded size is estimated as `manifest.decodedBytes × (that signal's chunk bytes ÷ all chunk bytes)` and compared with `viewer.eagerBudgetBytes` on its own. A 100k-span / 1M-log run keeps spans eager and puts logs windowed. No manifest change.
- **The trace index carries logs.** `TraceEntry` gains `logChunks: string[]` and `logs: number`. A trace that only has logs gets an entry with `spans: 0`; `hasTrace` means "has spans" (`spans > 0`). No `formatVersion` bump: each report ships its own viewer, `merge` reads only manifests and chunks (unchanged), and append already requires the same otel-html version.
- **Log identity is `<chunk>.<row>`** (`LogRef`, e.g. `12.345`) and is the URL key `log=`. It is stable for a given report folder; `merge` produces a new folder, so links into the old one do not apply to the merged one.
- **Severity facet.** "Only" writes a range pair (`log.severity_number >= SEVERITY_NUMBER_WARN and log.severity_number <= SEVERITY_NUMBER_WARN4`), and a third action, "and above", writes one `>=` token (the mockup's "severity ≥ WARN"). Excluding a band would need `or`, which the flat token model can't hold, so Exclude is disabled on severity rows and the tooltip points to the query bar.
- **Pattern → filter** uses OTTL itself: `IsMatch(log.body.string, "<regex from template>")`. `FilterToken` gains an op `matches` so the token stays editable and facets keep working.
- **Cross-signal carry-over.** When you move between explorers (sidebar, `g l`/`g t`, "Open in … Explorer"), only `t`, `text`, and a `q` that compiles in the target OTTL context come along. Everything else (mode, group, view, sort, trace, span, log, tabs) resets. A `q` that doesn't compile is dropped, and the target page shows a dismissible notice that names it. Within one explorer, everything is kept.

## Global Constraints

Everything in the M1 plan's Global Constraints still applies. Restated where M2 touches it:

- No `any`, no non-null assertions, exhaustive `switch` via `never`, typed `OtelHtmlError`s with `path`/`expected`/`actual`; Biome strict at error; `mise run check` < 60 s.
- Fail fast at every boundary: URL state (`log`, `ltab`, widened `mode`/`view`/`tab`), rollup and trace-shard payloads (Zod, `invalid-report`), log refs (`usage` "log 12.345 not found").
- Domain rules are data tables: default log facets, severity bands/labels/colors, log tabs, page modes and views, Drain masks and parameters.
- `file://` rules: no fetch/XHR/ES modules/worker files; all state in the URL; `localStorage` optional and wrapped in try/catch.
- Browser-safe dirs (`src/model`, `src/format`, `src/ottl`, `src/rollups`, `src/semconv`, `src/viewer`) never import `node:*`.
- Severity is from `SeverityNumber` ranges: 1–4 trace, 5–8 debug, 9–12 info, 13–16 warn, 17–20 error, 21–24 fatal, 0 unspecified (`severityKey`, existing). Display `ERROR · 17` (band label, then number); SeverityText is shown next to it when it differs from the band label.

- Only OTel fields: no log indexes or sources. Facets: Severity, Service, `host.name`, Scope, `event.name`, Has trace, attributes (§8.5).
- Embedded views **are** the explorer components (anti-goal: duplicated UI). The log list in trace/span Logs tabs and Surrounding logs is `LogList`; the log panel's Trace tab is `FlameGraph`.
- Targets (§16, ubuntu-latest, `OTEL_HTML_PERF_FACTOR` scaling as in M1): a 100k-span / 1M-log report opens to an interactive Trace Explorer in < 3 s; the Logs landing (windowed) in < 3 s; a one-window filtered log scan finishes in < 5 s; in-memory log filter or facet toggle < 150 ms (median, 200k logs); writer peak RSS < 512 MB; ≤ 200 bytes/log on disk.

### Task 1: Drain log patterns

**Files:**
- Create: `src/rollups/drain.ts`
- Test: `test/rollups/drain.test.ts`

**Interfaces:**
- Produces: `DRAIN_PARAMS = { depth: 4, similarity: 0.4, maxChildren: 100, maxClusters: 2000, maxTokens: 64 } as const`; `WILDCARD = '<*>'`; `DRAIN_MASKS: readonly RegExp[]` (whole-token: decimal numbers `/^[-+]?\d+(\.\d+)?$/`, hex ≥ 8 chars with optional `0x`, UUIDs, IPv4 with optional `:port`); `tokenize(body: string): { tokens: string[]; truncated: boolean }` (split on whitespace runs, mask tokens, keep the first `maxTokens`); `interface DrainCluster { id: number; tokens: string[]; truncated: boolean; count: number; severities: Record<LogSeverityKey, number>; first: number; last: number; sample: string }` (sample is the first body seen, cut to 256 chars); `class Drain { add(body: string, severity: LogSeverityKey, time: RelNanos): number /* cluster id, or -1 once maxClusters is reached */; clusters(): readonly DrainCluster[]; unclustered: number; toJSON(): SerializedDrain; static from(input: unknown, root: string): Drain }`; `template(c: DrainCluster): string` (tokens joined by one space, plus ` …` when truncated); `templateToRegex(c: DrainCluster): string` (`^` + escaped literal tokens joined by `\s+`, `<*>` → `\S+`, then `$` unless truncated).
- Algorithm: classic Drain. Tokens go through a fixed-depth prefix tree (layer 1 is the token count, then the first `depth − 2` tokens; a token containing a digit goes to a `<*>` child; at most `maxChildren` per node, with overflow into `<*>`). At the leaf, take the most similar cluster of equal length (share of equal tokens, wildcards excluded). At or above `similarity` it merges, and differing positions become `<*>`. Below it, a new cluster starts. Cluster ids count up from 0 in creation order and never change. `from` rebuilds the tree by re-inserting clusters in id order.
