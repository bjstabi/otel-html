# otel-html M4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship milestone M4 of otel-html: a dashboard schema in the config, dashboards carried in the report, a Dashboards list and dashboard page with the built-in Fusion dashboard, six widget types, variables, selection chips, follows-selection, Edit layout → Copy config, Views ▾ and Copy as dashboard widget.

**Architecture:** One Zod dashboard schema lives in a new browser-safe `src/dashboards/` module. The config schema embeds it, the writer validates it when config resolves and copies the resolved dashboards (with their source) into `manifest.config`, and the viewer parses them again from the manifest. Fusion is a constant in that schema. The viewer's dashboard page reads one URL key, `d` (variables, selection, per-widget overrides), and computes each widget's **effective scope** (condition, window, band, trace) with a pure function. It then renders each widget with the existing explorer components and query engines (`querySpans`, `queryLogs`, `runMetricQuery`, `MetricGrid`) inside a react-grid-layout grid.

**Tech Stack:** unchanged from M3, plus one runtime dependency, `react-grid-layout` 2.x (pin the newest 2.x release that is at least two weeks old). `yaml` (already a runtime dependency) is now also bundled into the viewer for Copy config.

**Spec:** `docs/superpowers/specs/2026-10-28-otel-html-m4-design.md`, on top of `docs/superpowers/specs/2026-10-25-otel-html-design.md` (§8.2, §8.3, §8.7, §9, §11.1, §16). Mockup: `docs/superpowers/specs/2026-10-25-otel-html-mockups/05-dashboards-fusion.html`. Conventions: the M1–M3 plans in `docs/superpowers/plans/`.

**Scope boundaries (M4 only):** No `+ Query` second query (only its hint text changes). No treemap, pie or point-plot widgets. No dashboard include files. No layout persistence. No receiver or live mode (M5).

**Plan-level calls (flag at review if wrong):**
- **New browser-safe dirs `src/query/` and `src/dashboards/`** (added to Biome's `noNodejsModules` override). `src/query/` takes the shapes that config and viewer now share and that currently live in the viewer:
  - the M3 metric query, formula and page-state Zod schemas and types;
  - the formula parser (`parseFormula`, `formulaRefs`);
  - `PAGE_OPTIONS`, `SELECTION_MODES` and `EXPLORER_VIEWS`.

  The viewer modules re-export them, so existing imports keep working, and knip still passes because every re-export is used.
- **Manifest:** `config` becomes `{ viewer, dashboards, views }`. `dashboards` is `{ source: string; dashboard: Dashboard }[]` and `views` is `View[]`. Both default to `[]`, and the new viewer keys (`defaultDashboard`, `home`) have defaults in the manifest schema, so M1–M3 manifests still parse. No `formatVersion` bump.
- **`viewer.defaultDashboard`** must name `fusion` or a config dashboard. A missing id fails at `viewer.defaultDashboard`, never in the viewer.
- **Widget ids** default to `w<n>` (1-based position) after parsing. The `d` URL key and Copy config use them.
- **Grid units:** row height 20 px and margin 10 px, so a widget of `h` rows is `h × 20 + (h − 1) × 10` px tall. The breakpoint for the stacked layout is 768 px.
- **Conditions are joined** with `andConditions(...)`, which wraps each non-null part in parentheses and joins with ` and `. A single part is returned as is, so URLs stay readable.
- **Variable conditions** are built with the existing `facetToken(key, 'resource', value, '==', kind, signal)` + `tokensToOttl`. Quoting and typed values therefore follow the explorers' facet rules. `kind` is the facet's recorded kind (`string` when only the metric catalog knows the key).
- **Trace condition:** `trace_id.string == "<hex>"` (the form `trace-logs-tab.tsx` already uses; valid for spans and logs).
- **`d` URL key** (JSON, Zod, like `m`):
  ```ts
  interface DashboardPageState {
    vars: Record<string, string | null>;
    sel: { t: string | null; trace: TraceId | null }; // t is the `<start>~<end>` form
    follow: Record<string, boolean>;
    logView: Record<string, 'matches' | 'context'>;
  }
  ```
  Every field defaults to empty, and a pristine state is omitted from the URL. The URL layer checks only the shape. Ids that are not on the dashboard, and a variable key that is not one of its variables, are reported by the page through `PageOptionNotice` with a Reset button.

## Global Constraints

Everything in the M1–M3 plans' Global Constraints still applies. Restated where M4 touches it:

- No `any`, no non-null assertions, exhaustive `switch` via `never`, typed `OtelHtmlError`s with `path`/`expected`/`actual`. Biome strict at error. `mise run check` < 60 s.
- Fail fast at every boundary:
  - config dashboards and views: Zod at resolve time, with issues at their path such as `dashboards[0].widgets[2].query`;
  - manifest dashboards: `invalid-report`;
  - the `d` URL key;
  - `localStorage` views: invalid content is ignored, never thrown.
- Domain rules are data tables:
  - `WIDGET_SCOPE` (the effective-scope rules);
  - `WIDGET_DEFAULT_SIZE`;
  - `WIDGET_DEFAULTS` (what Copy config omits);
  - `COPYABLE_VIEWS` (Copy as widget);
  - `FUSION` itself.
- `file://` rules; browser-safe dirs never import `node:*`; `localStorage` optional and wrapped in try/catch.
- The reuse rule: widgets render `ResultsTable` + `TRACE_COLUMNS_UI`/`SPAN_COLUMNS_UI`, `FlameGraph`, `LogList`, `MetricChartCard`, `MetricGrid`, `toplist()` from facet-views and `GroupTable`. No new list, chart or table implementations.
- Never silently wrong. Each of these produces a visible note:
  - a variable the metric lane ignores;
  - a metric not in the report;
  - partial scans;
  - a selection outside `t`;
  - hidden variables;
  - capped variable values.
- The design language of §8.1. Color follows the entity. Errors are never shown by color alone.
- Targets (ubuntu-latest, `OTEL_HTML_PERF_FACTOR` scaling): Fusion interactive < 3 s on the scale report, and a trace selection updates the Logs and Metrics widgets < 1 s.
- Conventional commits. Each commit message ends with the session's `Co-Authored-By` trailer.

### Task 2: Dashboard schema and Fusion

**Files:**
- Create: `src/dashboards/schema.ts`, `src/dashboards/fusion.ts`, `src/dashboards/conditions.ts`
- Test: `test/dashboards/schema.test.ts`, `test/dashboards/conditions.test.ts`

**Interfaces:**
- Consumes: `MetricQuerySchema`, `MetricFormulaSchema`, `MetricPageStateSchema`, `parseFormula`, `formulaRefs`, `PAGE_OPTIONS` (Task 1), and `compileCondition` from `src/ottl/compile.ts`.
- Produces in `schema.ts`, with explicit input and output interfaces as in `config/schema.ts` (`isolatedDeclarations`):
  - `type WidgetType = 'timeline' | 'traces' | 'logs' | 'metric' | 'toplist' | 'table'`.
  - `interface WidgetLayout { x: number; y: number; w: number; h: number }`.
  - `type Widget`, a discriminated union on `type`. The output shape always has `id: string` and `title: string | null`. Every type except `timeline` has `follow: boolean`. Per type:
    - `traces`: `{ query: string | null; text: string; mode: 'traces' | 'spans' }`
    - `logs`: `{ query: string | null; text: string; context: boolean }`
    - `metric`: `{ queries: MetricQuery[] | null; formulas: MetricFormula[]; display: 'lines' | 'area' | 'bars' | 'heatmap'; scale: 'linear' | 'log'; exemplars: boolean; echarts: Record<string, unknown> | null }`
    - `toplist`: `{ signal: 'spans' | 'logs'; query: string | null; text: string; groupBy: string; echarts: Record<string, unknown> | null }`
    - `table`: the same fields as `toplist` without `echarts`.
  - `interface Variable { key: string; label: string; default: string | null }`. String shorthand `'k'` → `{ key: 'k', label: 'k', default: null }`.
  - `interface Dashboard { id: string; title: string; description: string; variables: Variable[]; widgets: Widget[] }` and `DashboardInput`.
  - `interface View { id: string; title: string; page: 'traces' | 'logs' | 'metrics'; query: string | null; text: string; mode: string | null; groupBy: string | null; view: string | null; sort: string | null; metrics: MetricPageState | null }` and `ViewInput`.
  - `DashboardSchema: z.ZodType<Dashboard, DashboardInput>` and `ViewSchema: z.ZodType<View, ViewInput>`. Both use `strictObject` throughout.
  - `RESERVED_DASHBOARD_IDS = ['fusion'] as const`.
  - `DashboardListSchema` (a unique-id check plus the reserved check) and `ViewListSchema` (unique ids).
- Rules, as Zod refinements, each with the message given here:
  - id: `^[a-z0-9][a-z0-9-]{0,63}$`. Widget id: `^[a-z][a-z0-9-]{0,31}$`.
  - Bounds: `x + w ≤ 12` → `"x + w at most 12"`.
  - Overlap → on `widgets[j]`: `"does not overlap widgets[i] (<id>)"`.
  - Duplicate widget ids or variable keys.
  - At most 8 variables and 1–50 widgets.
  - `query` compiles in `span` (traces; toplist/table with `signal: spans`) or `log_record`. The message is `an OTTL condition valid for <spans|log records> (<compile error>)`.
  - Metric queries are 1–10, with non-empty `metric` and `show`. `formulas` require `queries`, and each formula parses and refers only to query ids that exist.
  - `follow` on a `timeline` is an unrecognized key.
  - View rules:
    - `mode` and `view` must be in that page's `PAGE_OPTIONS`;
    - `query` must compile in the page's context;
    - `metrics` is only allowed on `page: 'metrics'`;
    - `mode`, `view`, `query` and `text` are not allowed on `metrics`.
  - Widget ids default to `w<n>` in a transform after the per-widget parse.
- Produces in `fusion.ts`: `FUSION: Dashboard`, parsed once from a `DashboardInput` literal through `DashboardSchema` (spec §6.5 layout) at module load. The description is "Every signal on one timeline, with Traces, Logs and Metrics that follow your selection".
- Produces in `conditions.ts`: `andConditions(...parts: (string | null)[]): string | null` and `traceCondition(traceId: string): string`.
