# otel-html M3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship milestone M3 of otel-html: writer-side metric series at several resolutions, a metric query engine, the Metrics Explorer, the Catalog, and a Metrics tab in the log panel, the span section and the trace panel.

**Architecture:** The writer keeps storing every point verbatim in chunks (M1). M3 adds a metric pipeline beside it. Each point is assigned to a **metric definition** and a **series**, its temporality is normalized into a mergeable **bucket aggregate**, and the aggregate lands in a finest-level bucket. At every flush, the buckets accumulated since the last flush are spilled to a per-metric **segment** file. At close, each metric's segments are **compacted** into one file per resolution level plus an exemplar file. The catalog (definitions, series counts, sparklines) lives in `data/rollups/metrics.js`. The viewer loads one metric's files on demand and merges any segments it finds. A pure **query engine** turns them into chart series, and one **chart card** draws them in the Explorer and in the embedded grids.

**Tech Stack:** unchanged from M2. One new **dev** dependency: `@opentelemetry/sdk-metrics` (same release line as `@opentelemetry/sdk-trace-base` 2.12.0) for fixtures only. No new runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-10-27-otel-html-m3-design.md` (approved), on top of `docs/superpowers/specs/2026-10-25-otel-html-design.md` (§7.3, §7.5, §7.6, §8.3, §8.6, §9, §16). Mockup: `docs/superpowers/specs/2026-10-25-otel-html-mockups/04-metrics.html`. Conventions: the M1 and M2 plans in `docs/superpowers/plans/`.

**Scope boundaries (M3 only):** No "Copy as dashboard widget" (M4). No dashboards, Views ▾ contents or config-defined views (M4). No receiver or live mode (M5).

**Plan-level calls (flag at review if wrong):**
- **No `formatVersion` bump.** The manifest gains `metricFiles: string[]` with `.default([])`, so M1/M2 manifests still parse and `merge` keeps reading old reports. Each report ships its own viewer.
- **Paths use numeric metric ids, never names:**
  - `data/metrics/<id6>/series.js`: series definitions, rewritten when they change.
  - `data/metrics/<id6>/seg-<n6>.js`: finest-level buckets and exemplars since the previous flush.
  - `data/metrics/<id6>/l<k>.js`: level `k` after compaction.
  - `data/metrics/<id6>/ex.js`: exemplars after compaction.
  - Hostile metric names never reach a path.
- **Resolution ladder.** Level 0 is **1.024 s** (1 ms × 2^10, aligned like `TimeBuckets`); level k is 8^k × level 0. Compaction writes levels 0…K, where K is the first level with ≤ 2,000 buckets over the metric's time range (K ≤ 6). The viewer reads the coarsest level that still gives ≥ `maxPoints` buckets over the window, falling back to level 0.
- **Exemplar buckets are fixed at 65.536 s** (1 ms × 2^16). Each series keeps up to `writer.metricExemplars` (default 4) exemplars per bucket. Ones with a trace_id are preferred, then the most extreme values (two largest, two smallest).
- **Metric definition** = (name, unit, type, temporality, monotonic). The same name with another definition gets a new id, and the catalog marks every definition of that name as `conflicting`. **Series** = (definition, resource, scope, point attributes, explicit bounds). Resources and scopes are interned report-wide in the catalog.
- **First cumulative point of a stream:** when `start` is set, its full value counts as the delta (it counts since `start`). When `start` is null it is a baseline with delta 0.
- **Queries name metrics by name** (plus optional `kind`/`unit` when the name is conflicting), never by id, so URLs survive `merge`.
- **Counter `show` values:** `increase` is the delta per bucket, `rate` is the delta per second, and `sum` is the running total since the run start.
- **URL:** the Metrics page state is one key, `m`, holding a JSON object validated by Zod (`MetricPageStateSchema`). Hand-edited garbage gets the existing invalid-param notice, never a crash.
- **Carry-over:** going *to* Metrics carries `t`. A `q` that compiles in the `datapoint` context becomes the first query's `where`; otherwise it is dropped with the existing notice. Going *from* a chart's click menu to Traces/Logs carries the clicked bucket's window and the clicked query's `where`, through `carryTo`'s compile rule.

## Global Constraints

Everything in the M1 and M2 plans' Global Constraints still applies. Restated where M3 touches it:

- No `any`, no non-null assertions, exhaustive `switch` via `never`, typed `OtelHtmlError`s with `path`/`expected`/`actual`; Biome strict at error; `mise run check` < 60 s.
- Fail fast at every boundary: series, segment, level and exemplar files (Zod, `invalid-report` naming the file); the `m` URL key; config (`writer.metricSeriesCap`, `writer.metricExemplars`).
- Domain rules are data tables: `SHOW_BY_KIND`, `DEFAULT_SHOW`, combine-across-series rules, `METRIC_TYPE_LABELS`, metric namespace order, metric tabs.
- `file://` rules; browser-safe dirs never import `node:*`; `localStorage` optional.
- Single y-axis per chart; 2px lines; legend for 2+ series; hover crosshair; color follows the entity (service color for per-resource lines); errors never by color alone (§8.1).
- Embedded views **are** the explorer components (anti-goal: duplicated UI). The embedded grid uses `MetricChartCard` and `runMetricQuery`.
- Never silent wrong numbers: "other" series, resets, summaries at coarse levels, conflicting definitions, explicit histograms with different bounds, and missing exemplar traces each produce a visible note on the chart.
- Writer config defaults: `metricSeriesCap: 1000`, `metricExemplars: 4`.
- Targets (ubuntu-latest, `OTEL_HTML_PERF_FACTOR` scaling):
  - Metrics Explorer interactive in < 2 s on 200 metrics × 1,000 series × 1 h at a 10 s interval.
  - A query change re-renders in < 150 ms (median).
  - The Catalog opens in < 1 s.
  - Writer peak RSS < 512 MB including series state.
- Conventional commits; each commit message ends with the session's `Co-Authored-By` trailer.

## Review Focus

1. **Process restart mid-run.** A cumulative counter restarts with a new `start` and a lower value. Expected: no negative spike and no double counting. The series reports `resets: 1`, and the chart note says "1 counter reset". Two producers that share a series identity but have different `start`s are two streams, not alternating resets. Pinned in Task 2.
2. **Points with no value.** NaN or ±Inf gauge values, the `NO_RECORDED_VALUE` flag (bit 1), histograms with `count: 0`, and exp-histograms with only a zero bucket. Expected: they stay verbatim in chunks, stay out of aggregates (no NaN in JSON), and are counted as `noValue` on the series. The chart shows a gap, not a zero and not a crash. Pinned in Tasks 1 and 2.
3. **A report opened before close.** The writer was killed, or the report is read mid-run. Expected: segments only, no `l<k>.js` files, and the Explorer, Catalog and grids still chart every flushed point. Pinned in Task 4 (crash test) and Task 6 (loader merges segments).
4. **Cardinality over the cap.** 1,500 series for one metric with cap 1,000. Expected: 1,000 series plus one `other` series holding the rest. The Catalog shows "1000 + other". A `where` or `by` on an attribute renders a "partial: N series folded into other" note. Pinned in Task 3 and Task 7.
5. **Hostile metric metadata.** A metric name of `</script><img src=x onerror=alert(1)>`, a unit with `/../`, and attribute values with U+2028. Expected: data files stay valid scripts, paths use numeric ids, and everything renders as text in the picker, Catalog, legend and tooltip. Pinned in Task 4 and Task 13.

### Task 1: Metric bucket aggregates

**Files:**
- Create: `src/rollups/metric-agg.ts`
- Test: `test/rollups/metric-agg.test.ts`

**Interfaces:**
- Produces:
  - `type BucketAgg = NumberAgg | CounterAgg | HistAgg | ExpAgg | SummaryAgg`, discriminated by `k`:
    - `NumberAgg { k: 'number'; count: number; sum: number; min: number; max: number; last: number; lastTime: number }`
    - `CounterAgg { k: 'counter'; delta: number; resets: number }`
    - `HistAgg { k: 'hist'; count: number; sum: number; min: number | null; max: number | null; bounds: number[]; counts: number[] }`
    - `ExpAgg { k: 'exp'; count: number; sum: number; min: number | null; max: number | null; scale: number; zeroCount: number; zeroThreshold: number; positive: { offset: number; counts: number[] }; negative: { offset: number; counts: number[] } }`
    - `SummaryAgg { k: 'summary'; count: number; sum: number; quantiles: { q: number; v: number }[]; lastTime: number }`
  - `mergeAgg(a: BucketAgg, b: BucketAgg, path: string): BucketAgg` merges kind-by-kind:
    - Merging different `k`, or `HistAgg`s with different `bounds`, fails with `invariant`.
    - `ExpAgg` downscales both sides to the smaller scale. The result keeps at most 160 buckets per side, downscaling further if needed. The zero threshold is the larger of the two.
    - `SummaryAgg` keeps the quantiles with the larger `lastTime`.
  - `downscaleExp(e: ExpAgg, scale: number): ExpAgg`
  - `quantileOf(a: HistAgg | ExpAgg, q: number): number | null`:
    - Explicit buckets interpolate linearly inside the bucket, clamped to `[min, max]` when those are known. The open first and last buckets use `min`/`max`, falling back to the bound.
    - Exp buckets return the bucket's geometric midpoint.
    - Null when `count === 0`.
  - `BucketAggSchema: z.ZodType<BucketAgg>`. It rejects non-finite numbers, and checks `counts.length === bounds.length + 1` and that `count` equals the sum of the bucket counts (plus `zeroCount` for exp).

- [ ] **Step 1: Write failing tests:**
  - Merging two NumberAggs gives the summed `count`/`sum`, the min of `min`, and `last` from the later `lastTime`.
  - Merging two CounterAggs adds `delta` and `resets`.
  - HistAgg bounds `[0,5,10]` with counts `[1,2,3,4]`: `quantileOf(…, 0.5)` is in `(5,10]`. With `count: 0` it is `null`.
  - ExpAgg merge of scale 3 and scale 1 gives scale 1 with conserved `count`. A negative-only exp gives a negative p50.
  - Merging 1,000 alternating very small and very large values stays ≤ 160 buckets per side.
  - Mismatched bounds throw.
  - `BucketAggSchema` rejects `NaN` at `sum`, and a counts/bounds length mismatch.
- [ ] **Step 2: Run** `pnpm exec vitest run test/rollups/metric-agg.test.ts`. Expected: FAIL (module missing).
- [ ] **Step 3: Implement** `metric-agg.ts`. The exp index math follows OTLP: bucket `i` at scale `s` covers `(base^i, base^(i+1)]` with `base = 2^(2^-s)`, and downscaling by `d` maps index `i` to `i >> d`.
- [ ] **Step 4: Run** the test. Expected: PASS.
- [ ] **Step 5: Commit** `feat(rollups): mergeable metric bucket aggregates`.

### Task 2: Temporality normalization

**Files:**
- Create: `src/rollups/metric-streams.ts`
- Test: `test/rollups/metric-streams.test.ts`

**Interfaces:**
- Consumes: `BucketAgg` types (Task 1), `MetricPointRecord`.
- Produces:
  - `type Normalized = { kind: 'ok'; agg: BucketAgg; reset: boolean } | { kind: 'skip'; reason: 'out-of-order' | 'no-value' }`.
  - `class StreamNormalizer { normalize(seriesId: number, p: MetricPointRecord): Normalized; toJSON(): SerializedStreams; static from(input: unknown, root: string): StreamNormalizer }`.
- Rules (a data table keyed by `type × temporality × monotonic` → `'number' | 'counter' | 'hist' | 'exp' | 'summary'` handling plus `cumulative: boolean`):
  - **Gauge and non-monotonic sum** → `NumberAgg` of the point value.
  - **Monotonic sum:** delta → `CounterAgg`; cumulative or unspecified → difference from the stream's previous value. A drop is a reset: the delta is the new value, with `resets: 1`.
  - **Histogram and exponential histogram:** delta or unspecified → the point as is; cumulative → the difference of counts and sum. A drop in `count` is a reset.
  - **Summary** → `SummaryAgg`.
- A stream key is `${seriesId}:${start ?? 'none'}`. The first point of a stream is handled by the plan-level rule.
- **No-value**: flag bit 1 (`NO_RECORDED_VALUE`), a non-finite value, a non-finite sum, or a histogram with `count: 0` (only for delta, where it carries nothing).
- **Out-of-order**: only for cumulative streams, when `time ≤` the stream's last time.
- `SerializedStreams` holds every stream's last cumulative value or counts and its last time. The writer checkpoints it.

- [ ] **Step 1: Write failing tests:**
  - Cumulative counter points 5, 8, 2 (same start) → deltas 5, 3, 2, with `reset` on the third.
  - The same series with two starts interleaved (A 5, B 3, A 9, B 4) → deltas 5, 3, 4, 1 and no resets.
  - A null start gives a first delta of 0.
  - Delta points arriving in any order → all `ok`.
  - A cumulative point older than the stream's last point → `skip: out-of-order`.
  - NaN gauge, flag bit 1, and `count: 0` delta histogram → `skip: no-value`.
  - Cumulative histogram counts `[1,1]` then `[3,2]` → `[2,1]`.
  - `toJSON` then `from` continues a stream correctly.
- [ ] **Step 2: Run.** Expected: FAIL.
- [ ] **Step 3: Implement** `metric-streams.ts`. The point JSON (`p.point`) is parsed with a Zod schema per type (`asDouble`/`asInt`, `bucketCounts`, `explicitBounds`, `positive`/`negative`, `quantileValues`). Strings for 64-bit ints become numbers. A malformed point fails fast with `invalid-input` at its path.
- [ ] **Step 4: Run.** Expected: PASS.
- [ ] **Step 5: Commit** `feat(rollups): normalize metric temporality into mergeable deltas`.

### Task 7: The metric query engine and formulas

**Files:**
- Create: `src/viewer/data/metric-query.ts`, `src/viewer/data/metric-formula.ts`

**Interfaces:**
- Consumes: `LoadedMetric` (Task 6), `quantileOf`/`mergeAgg` (Task 1), `compileCondition(src, 'datapoint')`.
- Produces:
  - `type MetricKind = 'counter' | 'number' | 'hist' | 'exp' | 'summary'` and `kindOf(e: MetricDef): MetricKind`.
  - `SHOW_BY_KIND: Record<MetricKind, readonly string[]>` and `DEFAULT_SHOW: Record<MetricKind, string>`:

    | kind | show options | default |
    |---|---|---|
    | counter | `rate`, `increase`, `sum` | `rate` |
    | number | `avg`, `min`, `max`, `last` | `avg` |
    | hist / exp | `p50`, `p75`, `p90`, `p95`, `p99`, `count`, `sum`, `avg` | `p95` |
    | summary | `q<quantile>` per quantile present (e.g. `q0.99`), `count`, `sum` | the highest quantile |

  - `COMBINE: Record<MetricKind, …>`, the across-series rule (spec §6.1):
    - counters add.
    - hist merges per bounds set. Different bounds give separate lines, with the note "histogram bounds differ".
    - exp merges.
    - number: `avg` → mean of the series' bucket averages, `min`/`max` → extreme, `last` → **sum** of the series' last values.
    - summary is never combined: it is implicitly grouped by series, with the note "summaries are not combined".
  - `type MetricFn = { op: 'rate' } | { op: 'increase' } | { op: 'rollup'; agg: 'avg' | 'min' | 'max' | 'sum'; intervalMs: number } | { op: 'top' | 'bottom'; n: number; by: 'avg' | 'max' | 'last' }`
  - `interface MetricQuery { id: string; metric: string; kind: MetricPointRecord['type'] | null; unit: string | null; show: string; by: string[]; where: string | null; fn: MetricFn[]; alias: string | null; hidden: boolean }`. `by` holds OTTL paths: `resource.attributes["…"]`, `attributes["…"]`.
  - `interface SeriesPoints { key: string; label: string; group: Record<string, string>; unit: string; points: [number, number | null][]; resourceService: string | null }`
  - `interface MetricQueryResult { queryId: string; widthNs: number; series: SeriesPoints[]; exemplars: { time: number; value: number; traceId: string | null; spanId: string | null; seriesKey: string }[]; heat: { bounds: number[]; cells: [number, number, number][] } | null; distribution: { bounds: number[]; counts: number[] } | null; notes: string[] }`
  - `resolveMetric(catalog, q): { entry: MetricEntry } | { ambiguous: MetricEntry[] } | { missing: true }`
  - `runMetricQuery(m: LoadedMetric, q: MetricQuery, window: TimeWindow, maxPoints: number, signal?: AbortSignal): MetricQueryResult`:
    - `where` compiles once and is evaluated per series against a `DatapointTarget` built from the series def. `metric.name`, `metric.unit` and resource/attributes paths work. Time paths are unsupported in `where` and fail with `invalid-ottl` "time filters use the time range".
    - The level is picked by the plan-level rule.
    - Gaps are `null`.
    - Notes cover resets, `folded` with an attribute `where`/`by` ("partial: N series folded into other"), summaries at a level > 0, `fromSegments`, and `noValue`.
  - `parseFormula(expr: string): FormulaAst`: `+ - * /`, parentheses, numbers and query ids `[a-z]`. A bad expression fails with `usage` at its column.
  - `evaluateFormula(ast, results: ReadonlyMap<string, MetricQueryResult>, id: string): MetricQueryResult`: aligns on bucket time and group key. A group missing from one operand gives `null`, and division by zero gives `null`. All operands must share `widthNs`; the engine re-runs at the coarsest width among them.
