# The main report, front and centre (2026-11-04)

The link to the default branch's CI report (`https://bjstabi.github.io/otel-html/branch/main/`) is only reachable
through a run's jobs. This document says how it becomes the first thing a visitor to the repository sees: a link in
the About sidebar, a live status badge and a live screenshot at the top of the README. The process is **unattended**
(`docs/agents/process-unattended.md`): one PR, squash-merged when CI is green. Because the PR touches
`ci-report.yml` and the `otel-html-publish` action, which the unattended process otherwise stops on, the plan names
those changes and its approval covers them.

## Intent

A visitor should see at a glance that otel-html reports on its own CI, and reach main's live report in one click. The
badge and the screenshot are generated by the publisher on every default-branch publish, so they never go stale and
need no README commits. They double as product documentation: the screenshot shows what the tool makes, from real
data.

## Goals

1. **Sidebar** (no PR): `gh repo edit bjstabi/otel-html --homepage https://bjstabi.github.io/otel-html/branch/main/
   --description "OpenTelemetry traces, logs and metrics → a static, self-contained HTML report"`. The maintainer
   approved it; the coordinator runs it once the plan is approved.
2. **Badge data.** `ci site` writes a [shields.io endpoint](https://shields.io/badges/endpoint-badge) JSON file into
   the channel folder on every publish, one per workflow: `<channel>/badge-<slug(workflow)>.json`, from that
   workflow's newest run in the channel. Content:
   `{"schemaVersion":1,"label":"<workflow> report","message":"<mark> <duration>","color":"<color>"}` where, from the
   run's `conclusion`: `success` → `✓`, `brightgreen`; `failure` / `timed_out` / `startup_failure` → `✗`, `red`;
   `cancelled` → `cancelled`, `lightgrey`; anything else → the conclusion word, `lightgrey`. Duration is
   `updated_at − run_started_at` (falling back to `created_at`), formatted `4m12s` / `52s` / `1h03m`. A run without
   a `workflow` recorded gets no badge. Every user of the action gets these files at no cost; it is a pure function
   in `src/cli/ci/site.ts` with unit tests.
3. **Screenshot.** A new opt-in action input, `preview` (default `false`). When `true` and the run lands on a
   `branch/` channel (never `pr/`), the publish writes `<channel>/preview-light.png` and `<channel>/preview-dark.png`:
   headless Chromium, viewport 1280×720, device scale factor 2, `prefers-color-scheme` light and dark, of the
   channel's rolling report as it opens (the CI dashboard), taken after the report has finished loading (no
   `[aria-busy="true"]`, charts drawn). `ci-report.yml` sets `preview: true`.
4. **README.** At the top, under the title: the `ci` badge, and the screenshot as a `<picture>` switching on
   `prefers-color-scheme`, both linking to the report, with a one-line caption ("Live: this repository's own CI,
   reported by otel-html. Click to open."):

   ```md
   [![ci report](https://img.shields.io/endpoint?url=https://bjstabi.github.io/otel-html/branch/main/badge-ci.json&logo=opentelemetry)](https://bjstabi.github.io/otel-html/branch/main/)
   ```

   The README's publisher documentation describes the badge files and the `preview` input (the inputs table near
   line 511, the `ci site` row near line 375, the rolling-report paragraph near line 364).

## Non-goals

- A static badge beside the dynamic one (it would only duplicate it).
- Screenshots of pull request channels: each costs a browser install and a minute, and nobody links to them.
- Any change to the viewer, the report format or the public API.

## Anti-goals

- A failed screenshot must never fail or block the publish: the report, the link and the deploy are what matter. A
  failure is a `::warning::` and the previous screenshot stays on the site (so the README never shows a broken image
  once one exists).
- The screenshot must be in the same `gh-pages` push as the rolling report it shows: no second push, no extra lease
  race.
- No screenshot of the redirect stub: when the rolling rebuild falls back to the stub, the previous screenshot stays.

## Constraints and facts

- `ci site` runs inside `site-lease.sh`, which may retry the whole command on a fresh `gh-pages` checkout up to 5
  times. `rebuildRolling` → `clearRolling` deletes everything in `<channel>/` except `runs/`, so the badge files and
  the screenshots are deleted on every rebuild unless written after it (badges) or carried over (screenshots).
- The report opens from `file://`; no server is needed for the screenshot.
- The `report` job in `ci-report.yml` runs on `ubuntu-latest` (Node available, passwordless sudo). The browser comes
  from `npx playwright@<the version pinned in package.json, 1.64.1> install --with-deps chromium`, only when
  `preview` is `true`; no new npm dependency. External users of the action may run on runners without this; that is
  why it is opt-in, and a failed install is the same warning as a failed screenshot.
- Pages serves with `Cache-Control: max-age=600`; GitHub's image proxy follows it, so the README's images refresh
  within about ten minutes of a deploy.
- The README's images return 404 from the merge until the first default-branch publish after it (minutes). Accepted.
- The `report` job's `timeout-minutes: 15` must still hold; the browser install and two screenshots should add about
  a minute.

## Decisions made for the builder (the coordinator's calls)

- **Duration source.** `SiteRun` gains an optional `startedAt` (`run_started_at ?? created_at`), in the type and its
  zod schema (`exactOptional`, like `workflow`). `index.json` is the site's internal index, not the report format
  or the public API, so this is in scope. An entry written before the field exists gets a badge without a duration
  (message is the mark alone).
- **Newest run.** A workflow's badge comes from the first entry of that workflow in the channel's `runs` (already
  newest first by `completedAt`), not from the run being published; badges are rewritten for every workflow in the
  channel on each publish, after `rebuildRolling`, so a late older run never overwrites a newer result. Two
  workflow names that slug the same share a file; accepted.
- **What the screenshot step knows.** `ci site` writes one more output, `rolling=built|stub` (the README's `ci site`
  row says so). The screenshot runs only when `preview` is true, `channel` starts with `branch/`, and `rolling` is
  `built`. `clearRolling` keeps `preview-*.png` (and nothing else besides `runs/`), so the previous images survive
  a rebuild and a failed or skipped screenshot. These `ci site` changes are in scope; the non-goal is the viewer, the
  report format and `src/api`.
- **Install once, screenshot inside the lease.** A separate action step, before the site step and gated on
  `preview`, installs Chromium (`continue-on-error`, its outcome passed on). Inside the lease command, after
  `ci site`, the screenshot script runs; it always exits 0, printing a `::warning::` on any failure (including a
  missing browser). Holding the lease ~20 s longer only widens the optimistic-push window; a rejected push retries
  as today.
- **Playwright version.** Hard-coded in `action.yml` (`npx -y playwright@1.64.1 …`), with a unit test that fails when
  it differs from `@playwright/test` in `package.json`, so a dependency bump updates both. `--with-deps` always; a
  failed install is the warning above.
- `actions-smoke.yml` stays as it is.

## Left to the builder

- Where the screenshot code lives (a script beside the action, called after `ci site` inside the lease command, is
  the expected shape) and how it waits for readiness, within the constraints above.
- How the previous screenshots survive `clearRolling` and failures (for example: skip them in `clearRolling`, or
  move them aside and back).
- How the screenshot path is tested: at minimum a test that runs it against a fixture report and checks it writes two
  non-blank PNGs of the expected size, in a job that already has Chromium.
- Exact duration formatting edge cases and the badge test cases.
- The PR: branch `feat/main-report-showcase`, title `feat(ci): a live badge and screenshot of the default branch's
  report`.
